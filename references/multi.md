# 多人直播：已有转写稿与对应回放

这是多人流程的开发候选。工具与受控结构样例可验证，真实多人素材由用户留待后续统一验收。不得宣称真实长场质量已通过。暂不自动转写整场、不运行固定两类的双人声音聚类，不上传素材或调用新云服务。

先读取 [通用整理规则](general.md)，直接复用其中的原意、数字、案例、限定条件、观点归属、原声疑点和逐段反查要求。多人流程增加人物、逐块归属、覆盖和交付检查；不另造一套简化提示词。

## 1. 取得原稿并准备材料

需要可读取的回放和带时间、说话人标记的原转写。已有原稿优先使用，只核对疑点，不重复转写整场。纯文本格式为“发言人1  00:00”独立标题行及后续原话；同秒保留原顺序和独立编号，不改时间。SRT/VTT沿用内置字幕导入合同；未标注声音、跨人同块或不清楚的字幕须先保留原件核对，不能伪造标签。

原标签数量只用来准备候选人物，不证明实际声音数。若用户已说明多人但原稿少于三个标签，可用`--participants`提供候选人数，随后仍须逐人以回放核对。实际仅一人或两人时，保留多人候选现场，以同一原始输入建立独立的单人/双人场次，不把多人片段清单交给旧工具，回到原流程；无法确认时保持待核，不猜。

以下路径中的`SKILL_ROOT`为本Skill实际安装根目录，`CASE`为安装目录外的新场次。

```text
python "<SKILL_ROOT>/scripts/multi_livestream.py" init --case "<CASE>" --replay "<回放>" --transcript "<原稿>" --layout discussion
```

- 多人对谈、圆桌、播客使用`discussion`；依次上台分享使用`sequential`，保留原发言顺序。
- 已有词库可加`--profile "<资料目录>"`，继续使用原核心的资料快照。
- 已知至少三位参与者但标签发生合并时，可加`--participants 3`。这是待核线索，不是已识别人数，也不是固定上限。
- 原件只读。初始化复用原核心的复制、原始时间与字幕转换、来源绑定及资料快照；失败不覆盖原场次。

初始化生成`_work/多人回听入口.md`、音频片段、`_work/多人任务.json`和`_work/多人编辑记录.json`。所有人物、实际核对和正文初始均待填写；工具不代填已经回听。

继续旧场次使用`prepare "<CASE>"`，来源一致时保留编辑记录和既有音频。来源变化时拒绝复用，不重新生成索引来掩盖差异。

## 2. 先核对人物与必要原声

打开回听入口，核对开场、25%、50%、75%、结尾，并核对每个原标签的首次出场。同秒换人额外保留独立原文位置；固定抽样不代表已经发现所有短暂出场的人物。

在`多人编辑记录.json`填写实际发生的事实：

- `reviews`：每条写`clip_id`、实际`method`（真人回听、音频理解或回放画面）、`reviewer`、具体`finding`，以及此次确实核对的`checked_source_ids`。只听过同一音频不能自动确认后来增加的原文位置。工具仅核查记录与材料的对应，不能验证“真的听过”这个主张，Agent不得补造。
- `participants`：稳定编号、显示称谓、原标签线索、真实`basis`和`review_ids`。核对后将`status`设为`confirmed`，表示声音/称谓已区分；名字未核实时保留“发言者1”等中性称谓，不把确认声音写成确认实名。
- 新发现的人物可以加入人物表，不限两位。没有独立原标签的人物将`source_labels`留空，填写其`first_source_id`并关联实际回放核对；不能为了通过检查改写原稿标签。
- `blocks`：按原顺序填写各块的`speaker_ids`。默认标签与实际人物冲突、同块多人或同秒发言，都须给本块的`review_ids`；同一原文块可关联多位已核人物，正文仍分别保留归属。

发现额外疑点时提取该原文位置的音频，不重新处理整场：

```text
python "<SKILL_ROOT>/scripts/multi_livestream.py" clip "<CASE>" --block "<原稿块编号>"
```

实际没有音频理解能力时，把入口和具体疑点集中交给用户核对。未收到真实结论前保持待核；不能用原标签、ASR一致或五句不同文字证明人数。

## 3. 通读全场，盘点后再编辑

逐块的`outline`记录话题和真实原句：`topic`为本块话题；`anchors`记录`kind`及原文中实际存在的`quote`。类型可选观点`point`、例子`example`、限制`limit`、提问`question`、分歧`opposition`、收束`ending`和数字`number`。重要否定、限制和数字尽量保留原词，不能在稿件写完后倒填一份看似完整的盘点。

轮流分享保留各人完整的讲述和承接；多人对谈保留谁问、谁答、谁追问、谁补充、谁不同意。不要把少数意见删掉，也不要为了篇幅均等添加无效内容。同秒不等于同时发声；实际听不清的重叠保留疑点，不编造先后。

随后分别填写`full_draft`和`reading_draft`。每段有唯一`id`、`speaker_id`、实际`source_ids`和正文`text`。一段不能跨人拼接，来源顺序不能被后来的合并打乱。阅读稿保留有效底稿，普通摘要不能冒充完整阅读稿。

不进正文的原文块仍保留在原件和逐块记录中。`include=false`时必须有`exclusion`，写明`category`（口头噪音filler、运营operations、偏题off-topic）、具体`reason`、`confirmed_by`及对应原声`review_ids`。不能随便删内容来提高比例。

`issues`保留独立问题：`id`、P0/P1/P2、`source_ids`、`question`、`status`。重要疑点需有可打开的原声位置；用clip补齐。真实解决或保守处理后，写`resolution`、`review_ids`和当前正文确实采用的`adopted_text`；没有依据不关闭。

从原稿逐项反查事实、归属、覆盖、案例、限制、问答和结尾，独立通读后填写`whole_review`：实际检查人、具体发现及`checks`（facts、attribution、coverage、examples、limits、questions、ending）。这不是人工发布终审。

## 4. 生成、检查和导出

```text
python "<SKILL_ROOT>/scripts/multi_livestream.py" render "<CASE>"
python "<SKILL_ROOT>/scripts/multi_livestream.py" audit "<CASE>"
python "<SKILL_ROOT>/scripts/multi_livestream.py" export "<CASE>" "<阅读副本目录>"
```

用户主要收到`outputs/01_公众号可发布稿.md`和`02_待核问题清单.md`两个Markdown。第一份是待发布稿，文件名不代表终审。质检报告、完整底稿、覆盖表、证据映射、编辑台账、人物与时间轴、原文索引和回听材料保留用于反查。

这里的多人工具复用原导出器，检查链接、复制必要核对音频并保留已有人工阅读稿。手工修改过的正文或材料不会被再次render覆盖；先比较并明确承接人工版本，不以旧记录覆盖真人稿。

多人使用本工具的audit，不运行旧双人审计或固定两类声音处理来取得通过。自动检查会发现缺人、串人、顺序变化、遗漏原文块、关键原句丢失、过度压缩、数字新增、资料或原声变化、缺少核对记录等结构异常；字词比例不能证明语义完全忠实，仍需真实原声核对和通读。

## 5. 人工终审与当前验收状态

P0未清零不能交付；未关闭P1仍须明确呈现，不能宣称可发布。正式发布前以真实人工结论填写`_work/多人终审.json`，包含`reviewer`、`reviewed_at`、`basis`、`decision=approved`，及本次主稿`draft_sha256`、编辑记录`record_sha256`。仅在真人确实完成终审后记录，Agent不得自己批准。再次改稿会使旧终审失效。

```text
python "<SKILL_ROOT>/scripts/multi_livestream.py" audit "<CASE>" --release
```

受控三人、六人、同秒、标签混乱及反例测试不是真实文稿质量验收。用户明确将真实多人素材留待后续统一验证；此阶段不调用云端、不上传私人案例、不宣称仅音视频的自动多人识别已完成。现有单人/双人流程保持原实现。
